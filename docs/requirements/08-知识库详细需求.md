# 08 知识库详细需求

## 目标

Knowledge Base 负责把个人资料变成可检索、可追溯、可被 Agent 使用的知识资产。它既要支持传统文件浏览，也要支持基于 LLM 的问答和整理。

## 支持的资料来源

第一阶段资料来源：

- Markdown 文件夹。
- Obsidian Vault。
- PDF 文件。
- 网页剪藏文本。
- 手工创建的文本笔记。

扩展来源：

- HTML。
- DOCX。
- 图片 OCR。
- 情报中心条目沉淀。
- Agent 对话沉淀。

## 导入流程

导入步骤：

1. 用户选择文件或目录。
2. File Importer 记录来源。
3. Parser 识别文件类型。
4. Extractor 抽取正文和元数据。
5. Chunker 分块。
6. Keyword Index 建立关键词索引。
7. Embedding Service 生成向量。
8. Vector Store 写入向量。
9. App SQLite 写入文档、chunk 和索引状态。

导入必须保留来源路径和文档 hash。文件内容变化后需要标记为待重建索引。

## Chunk 策略

Chunk 需要同时考虑语义完整性和检索效率。

建议规则：

- Markdown 按标题层级和段落切分。
- PDF 按页码、段落和长度切分。
- 代码文档按标题、列表、代码块边界切分。
- 每个 chunk 保留 `documentId`、位置、标题路径和文本 hash。
- 长文档允许 overlap，但 overlap 不应破坏来源引用。

## 检索方式

支持三种检索：

- Keyword Search：适合精确词、标题、标签、路径。
- Vector Search：适合语义问题。
- Hybrid Search：合并关键词与向量结果，作为默认问答检索。

检索结果需要展示：

- 文档标题。
- 来源路径。
- 命中片段。
- 分数。
- 更新时间。
- 所属标签或标题层级。

## RAG 问答

RAG 问答流程：

1. 用户提出问题。
2. Query Normalizer 处理问题。
3. Keyword Search 和 Vector Search 并行检索。
4. Ranker 合并结果。
5. Context Builder 控制上下文长度。
6. LLM Provider Adapter 生成回答。
7. 返回答案、引用来源、相关文档和置信提示。
8. 保存问答记录。

回答要求：

- 必须展示来源引用。
- 当检索结果不足时明确说明。
- 不把无来源推测伪装成知识库事实。
- 支持把回答保存为笔记。

## Obsidian 兼容

Obsidian 支持边界：

- 读取 Vault 目录。
- 识别 Markdown 双链。
- 识别 tags。
- 保留原始文件路径。
- 导出新笔记到指定目录。

第一阶段不强制实现完整 Obsidian 插件协议。

## 与 Agent 的关系

Agent 可以通过工具使用知识库：

- `kb.search`
- `kb.ask`
- `kb.getDocument`
- `kb.saveNote`

Agent 使用知识库时必须保留引用来源，并记录工具调用日志。

## 错误与恢复

错误场景：

- 文件不存在。
- 文件读取失败。
- PDF 解析失败。
- Embedding Provider 不可用。
- Vector Store 不可用。
- 索引中断。

恢复策略：

- 单文件失败不阻断整个目录索引。
- 失败项进入索引报告。
- 可对失败文档单独重试。
- Provider 缺失时可先建立关键词索引。

## 第一阶段验收口径

- 知识来源、导入、索引、检索和问答流程清晰。
- Chunk、Keyword、Vector、Hybrid Search 的关系明确。
- RAG 回答有来源引用规则。
- Agent 调用知识库的边界明确。
